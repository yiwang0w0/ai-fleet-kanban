# 方案:按身份分配工作 —— 把「主管 / 架构师 / 码农 / 对抗评审」接进看板

> 2026-09-28 · 状态:§7 四项已裁定;**P1 已实现(v0.22.0)、P2 已实现(v0.23.0),均在本分支**;P3 只测量,待远程机跑三个真实目标。
> §6 的缺口已修(v0.21.2)。
> 参照物:操作者的《多模型协作计划(执行机 = 远程电脑)》。那份计划的 §1 把「任务分发」标为
> 未落地 —— 这块看板就是那一层,已落地;本文只回答它缺的那部分:**线为什么还没有身份,
> 以及怎样让工作按身份、按确定性规则分派**。
> 先看了 9 个同类开源项目与 4 篇论文 / 实践帖(§1),再对照本仓代码(§2),然后才是设计(§3)。

## 0. 结论

1. **那份计划的五个角色,看板已有三个半。** 码农 = 线(worker line);对抗评审(实现后)= 自动审阅座席(每卡新会话、无 Edit/Bash、先跑 `verify_cmd`、机器产出闸,且能以 codex 座席运行);人三闸 = 通过 / 打回、`human_gate`、handoff;任务分发 = 看板本体。资料整理员是那边的 L0 层,与看板无关。
2. **真正缺的是两样,而且都不是「再加一个角色」:**
   - **线没有身份。** 今天一条线只有 `id / hint / label / accept`;座席(runtime / model / effort)是运行时设置(`worker_settings.json`),不是线的属性;提示词全线一份;工具集全线一样(`WORKER_TOOLS` 常量)。所以「架构师只读、码农可写、评审者换家族」在配置里说不出来。
   - **跨身份的流水线没有确定性表达。** 「先审方案再拆解」「评审者必须与作者不同家族」今天只能靠人记得。拆解器给子卡选线靠一段 hint 让模型猜,猜错的域门兜底(落成 null),但没有更好的输入让它猜得准。
3. **同类项目的共识(§1):身份 = 章程(散文)+ 工具档(唯一能被机器强制的部分)+ 座席映射(主 / 备 / 评审家族、反亲和);分派要由声明决定,不要让一个模型当经理去调度**(Bernstein 作者实测:40% 的 token 花在协调上,还会幻觉出优先级)。这与本仓「结构优先于纪律」「卡上不写模型名」的既有立场一致。
4. **交叉评审的证据是不对称的**(§1.3):Claude 审 Codex 显著有效,Codex 审 Claude 反而变差;而对**方案**做结构化对抗评审是所有拓扑里得分最高的。⇒ 跨厂商的价值放在**方案阶段**(Astra 审方案),代码阶段的自动审阅座席用 Claude。反过来配是花钱买退步。
5. **分三个阶段**,每阶段一个 minor 版本、一组没它就红的 harness 断言;机器名全部**新增不改名**,GLOSSARY 的冻结不破。第三阶段只做测量,不做功能 —— 与那份计划的 P3 前提一致(n=1 不作结论)。
6. **动工前先修一个已实测的缺口**(§6):v0.17.0 的路径 deny 规则在 POSIX 上因为写法(单斜杠 = 项目根相对)一条都不生效;Linux/macOS 部署的 Claude 座席今天可以读令牌、改登记簿。本方案的「只读身份」要复用同一机制,所以先修、先量,再动 P1。

### 1.2 讨论帖

- [Stop using LLMs to schedule other LLMs](https://dev.to/alex_chernysh/why-i-stopped-using-llms-to-schedule-llms-4176):模型经理 = ~40% token 花在协调、幻觉优先级、延迟高;改成确定性调度后稳定运行数月。
- [Cross-Model Adversarial Review(实践)](https://codex.danielvaughan.com/2026/03/28/cross-model-adversarial-review/):critic **新会话**、只给 diff + spec、输出 `PASS` 或带 file:line 的违规清单;复用会话 = 锚定偏差。这与本仓审阅座席「每卡新会话」完全同形。
- 中文社区([80aj 多角色协同流](https://www.80aj.com/2026/08/31/ai-claude-codex-dev-flow/)、[知乎:一个人指挥三个 AI](https://zhuanlan.zhihu.com/p/2016246103780111915)):共同做法是 Claude 拆解 / 架构、Codex 实现或审查、人做终审;共同痛点是**上下文交接与结果校验**,没有一篇解决「谁审谁」的机器强制。

### 1.3 论文(决定了 §3.2 的默认配置)

- [Cross-Model LLM Code Review(2607.21656)](https://arxiv.org/abs/2607.21656):116 题、六组对照。Claude 审 Codex:71.6% → 89.7%(p=.001);**Codex 审 Claude:91.4% → 82.8%(p=.046,变差)**;Claude 自审无提升。结论:「有用的配对是不对称的:用 Claude 审 Codex,不要反过来」。
- [LLM Consortium for Software Design Refinement(2606.01490)](https://arxiv.org/abs/2606.01490):520 次运行、12 种拓扑。**结构化对抗(v4b)最高 4.637**,跨模型评审次之 4.606,**并行合并最差**(3.65–3.79)。不同家族的评审员对同一设计打分差异大 —— 评审员多样性有价值,但价值在**方案 / 设计层**。
- [Adversarial Review: Structured Disagreement(2608.18167)](https://arxiv.org/abs/2608.18167):三角色(coder / reviewer / critic)优于五角色;朴素对抗会出现「假共识」,要求分歧必须有证据。⇒ 评审输出要求逐条引原文 / file:line,不接受泛泛的「看起来对」。

## 2. 现状对照:那份计划的角色 ↔ 看板

| 计划里的角色 | 看板今天 | 缺口 |
|---|---|---|
| 主管(人 + 聊天模型;`docs/方案-<slug>.md`,commit 即冻结) | 目标卡(`kind=goal`),正文就是方案;`bless` 冻结的是治理代码,不是方案 | 方案文件协议可以原样沿用(见 §3.3):文件冻结方向,卡引用文件 + 提交哈希 |
| Astra(方案对抗评审 + 写任务文件;codex 只读) | 拆解器(`decompose_lib.js`,只走 claude,`decompose_models`);自动审阅只在**交付后** | **没有交付前的方案评审**;拆解器不能跑 codex;没有「只读身份」的线 |
| 码农(`claude -p` 读 task) | worker 线:claude / codex 座席、阶梯提权、心跳、租约、指纹刹车 | 提示词全线一份、工具集全线一样、没有章程 |
| 对抗评审(实现后,`codex exec review --base main`) | 审阅座席(`roles:["review"]`):新会话、无 Edit/Bash、先跑 `verify_cmd`、机器产出闸;`WORKER_RUNTIME=codex` 即 codex 只读审 | **没有反亲和**(审阅者可能与作者同家族);单座席全板通用,不能按线指定 |
| 人三闸(冻结前 / 放行前 / 合并前) | 通过 / 打回、`human_gate`、handoff 回执 | 无 |
| 任务分发(那边的任务 #21,未落地) | 看板本体(SQLite 队列、认领、DAG `blocked_by`、审计 `task_events`) | 无 —— 这就是它 |

代码里的具体锚点(按内容定位,不按行号):

- 线的全部属性:`server.mjs` 的 `rebuildLines()`(`LINES / LINE_HINT / LINE_LABEL / LINE_ACCEPT`)与 `addLine()`;
- 座席只在运行时设置:`slotEnv()` 从 `worker_settings.json` 的 `agents[]` 取 `WORKER_MODEL / WORKER_EFFORT / WORKER_RUNTIME`;
- 提示词单一模板:`worker_loop.py` 的 `build_prompt()`;工具集常量 `WORKER_TOOLS = ["Read","Write","Edit","Glob","Grep"]`,argv 在 `cli_argv()`;
- 已有的「按线注入的持久材料」:`context_lib.py`(`BOARD_BASELINE_DOCS` 哈希钉住、逐字内联 —— **只对 codex 生效**)和线锚点(`lineage.json` 的 `anchor`);
- 拆解菜单:`decompose_lib.lineMenu(lines, hints)`;
- 审阅队列:`store.pendingReview()`(纯 SQL + 交付指纹,不看线);卡上已有 `last_runtime`(claim 时记的实际运行时)。

## 3. 设计:线 = 身份

### 3.1 配置形状(`lines[].role`,全部新增键,可选)

```json
{
  "id": "astra", "label": "架构", "hint": "审方案:只指出会在哪里崩、哪些假设没验证",
  "role": {
    "kind": "review",
    "tools": "read-only",
    "charter": "docs/roles/astra.md",
    "seat": { "runtime": "codex", "model": "gpt-6-astra", "effort": "high" }
  }
},
{
  "id": "engine", "label": "引擎", "hint": "代码/SQL/迁移",
  "role": {
    "kind": "implement",
    "tools": "write",
    "charter": "docs/roles/engine.md",
    "seat": { "runtime": "claude", "model": "claude-opus-5", "effort": "high" }
  }
}
```

每个键是什么、是结构还是纪律 —— 照 cc-orchestrator #427 的教训,写清楚不假装:

| 键 | 域(闭域,未知值拒绝) | 兑现方式 | 结构 / 纪律 |
|---|---|---|---|
| `kind` | `implement` / `review` | 决定提示词模板:`review` 用「你不做活,只读证据下判断」的框架,交付物 = 评审文本(卡的证据);拆解菜单按 kind 分组,子任务只从 `implement` 线里选 | 结构(模板由 kind 选) |
| `tools` | `write` / `read-only` | Claude 座席:`read-only` = `--allowedTools Read Glob Grep Write` + `--disallowedTools "Edit(//<repo 绝对路径>/**)"`。**写法照 §6 的实测**:绝对路径用双斜杠 `//`,单斜杠是「项目根相对」,不会匹配;`Edit(path)` 已覆盖 Write / NotebookEdit,`Read(path)` 已覆盖 Grep / Glob,`Write(path)` / `Glob(path)` 两种写法 CLI 明说不匹配。证据文件不在 repo 里,不受这条影响。codex 座席:`codex_runtime.argv(..., mode="read-only")`(审阅座席已在用) | **结构**(唯一被机器强制的部分) |
| `charter` | 仓库相对 `.md` | 逐字内联进每次提示词,**哈希钉在清单里**(复用 `context_lib` 的 manifest 机制,扩到 claude 座席);章程被改而未验收 ⇒ 领卡前 fail-closed(与基线同一极性) | 纪律,但「验收过哪一版」是结构 |
| `seat` | 座席宣言值域(`runtimes[]`) | 线**首次**启动时作为 `agents[0]` 的缺省;之后 `worker_settings` 照旧优先;面板在与身份缺省不一致时标「偏离身份缺省」 | 缺省 + 可见,不是强制 |

**为什么放 `lines[]` 而不是新表 / 新端点:** 线已经是认领过滤器、拆解菜单、面板徽章、账本维度的共同键;身份挂在同一个键上,就自动出现在所有已经按线分叉的地方。`add-line` skill 的护栏(一次加一条、不改 id、不删线)照旧适用。

### 3.2 反亲和:评审者 ≠ 作者家族

- 配置:`"review": { "anti_affinity": "runtime" }`(可选;不配 = 今天的行为)。
- 实现:`reviewer_loop.py` 取到待审列表后,跳过 `last_runtime == RUNTIME` 的卡,并**出声**:`跳过 #N:作者与审阅同家族(claude)`。`store.pendingReview()` 保持纯净不改 —— 这是座席的策略,不是队列的定义。
- 被跳过的卡留在「待验收」给人看(面板标「待异族审阅」),不丢、不静默。
- **默认配置照证据给**(§1.3):审阅座席 = claude;方案评审线(`astra`)= codex 只读。若操作者把两边配反,`doctor` 打一行警告并引用那篇论文的数字 —— 不拦,只说。

### 3.3 流水线:方案 → 对抗评审 → 拆解 → 实现 → 自动审阅 → 人

全部用**已有原语**拼(目标卡、子卡、`blocked_by`、`human_gate`、`verify_cmd`),不引入新状态、不引入第二套文件真相:

1. **方案文件照那份计划的协议**:`docs/方案-<slug>.md`,commit 即冻结。目标卡的正文写「方案:`docs/方案-<slug>.md` @ `<commit>`」—— 方向在文件里冻结,队列在看板里。
2. **评审卡由模板生成**(`POST /api/goals/:id/pipeline`,或面板目标卡上的「起流水线」按钮):在 `astra` 线下建一张 `kind=review` 子卡,验收写死为「逐条引方案原句,列出会崩的点与未验证的假设;不改任何文件」。评审文本 = 卡的证据 = 正史;要落成 `docs/评审-<slug>.md` 时由协调席导出,不让只读线往仓库写文件。
3. **拆解闸**:目标卡下有未完成的 `review` 子卡时,`/decompose` 拒绝(409,`needs_force`),人看过评审、改过方案后再拆 —— 这就是那份计划的第一道人闸「方案冻结前」。
4. 拆解出的实现子卡照旧(`blocked_by` 表顺序),自动审阅照旧,通过 / 打回归人。
5. 「实现后由另一家族审 diff」= §3.2 的反亲和 + 现有审阅座席;不另做 `review --base main` 通道 —— 审阅座席已经在新会话里读仓库现物,再加一条 diff 通道是两个评审者互相不知道对方说过什么。

**不做任务文件协议(`dispatch/inbox/*.task.md`)**:看板本身就是队列与状态机,再加一层文件 = 两套真相;那份计划里 task 文件的必填字段(`slug / assignee / allowed_tools / done_when / 失败上限`)一一对应到卡的 `subject / line / role.tools / acceptance+verify_cmd / max_attempts`。

### 3.4 拆解按身份

- 菜单从 `id (hint)` 变成 `id(label · kind · hint)`,且只列 `kind=implement` 的线;模型选线仍由既有域门校验(未知 → null 并记在卡面)。
- **不做**按文件路径 / 关键字的确定性选线:vibe-squad 的 `write_scope` 那种做法要先有数据说明拆解器选错了多少 —— 那是 §4 P3 要量的东西。

## 5. 不做的事,与理由

- **不做模型经理**(一个 LLM 在运行时决定谁干什么):§1.2 的 40%,以及本仓「拆解结果经域门、裁定归人」的既有裁定。

## 6. 动工前的核查:v0.17.0 的 deny 规则在 POSIX 上不生效(已实测)

写本文时先怀疑的是「规则覆盖了证据目录,证据写不出来」;在本会话的容器里(Linux,Claude Code **2.1.283**,`-p` 模式,Haiku,临时目录,共 14 次最小调用)量出来的是另一件事,更严重:

| 规则写法(`--disallowedTools`) | 工具 / 动作 | 结果 |
|---|---|---|
| `Edit(/abs/data/**)`(单斜杠,= `cli_deny_rules` 今天在 POSIX 上产出的形) | Edit 改现有文件 / Write 覆盖 / Write 新建 | **全部成功,未拦** |
| `Read(/abs/data/**)`(单斜杠) | Read 读密文 / Grep 搜密文 | **全部成功,未拦** |
| `Write(/abs/…)` `Glob(/abs/…)` | — | CLI 打警告:这两种写法「不被文件权限检查匹配」,只认 `Edit(path)` 与 `Read(path)` |
| `Edit(//abs/data/**)`(双斜杠) | Edit / Write 覆盖 / Write 新建 | **全部拒绝** |
| `Read(//abs/data/**)`(双斜杠) | Read / Grep | **全部拒绝**(Read 规则覆盖 Grep) |
| `Edit(denytest2/data/**)`(cwd 相对) · `Read(/denytest2/data/**)`(项目根相对) | Edit / Read | 拒绝 |

解释:Claude Code 权限规则里 `/path` 是**项目根相对**,`//path` 才是绝对路径。`verify_lib.cli_deny_rules()` 用 `os.path.abspath(...)` 生成规则,POSIX 上得到单斜杠 ⇒ 被解释为 `<项目根>/home/user/…/core/.data/**`,永远不匹配。v0.17.0 的九组实测在 Windows 上做(`C:/…` 形),那边成立;Linux/macOS 上这道「结构防线」从 v0.17.0 起就是空的,而 doctor 只核对 `--disallowedTools` 这个旗存在,不核对规则语义;所有 harness 驱动的是桩,桩不执行 deny。**这是本仓自己的 CI 结构性盲区**(Linux lane 存在正是为了抓这类事,但它抓不到「旗接受了、语义没兑现」)。

补量(同一容器,再 6 次调用)决定了修法的范围:

| 规则 | 动作 | 结果 |
|---|---|---|
| `Read(//D/**)` 单独 | Write 新建 `D/evidence/x.md` · Write 新建 `D/x.md` | **都被拒**(Write 工具先按 Read 规则查路径) |
| `Read(//D/*)` 单星 | Write 新建子目录文件 | 拒(单星也盖住子目录) |
| `Edit(//D/existing.json)` 逐文件 | Edit 该文件 · Write 新建 `D/evidence/x.md` | 拒 · **放行** |
| `Read(//D/board.db*)` 文件名通配 · `Read(//D/probes/**)` 子目录通配 | Read `board.db-wal` · Read `probes/p1.txt` · Write `evidence/x.md` | 拒 · 拒 · **放行** |

⇒ 整目录一网打尽的写法与「证据目录留给模型」不能共存;唯一能同时成立的是**逐文件 / 文件名通配 / 子目录通配**。

已修(v0.21.2,本分支):

1. `verify_lib.deny_path()`:POSIX 绝对路径拼成 `//…`;Windows 的 `C:/` 形保留(未在此复测)。
2. `verify_lib.cli_deny_rules()`:只产 `Read` / `Edit`;按 `PROTECTED` 表逐文件钉(三令牌、`board.db*`、`accepted_rev`、`restart_from`、座席设置、`lineage.json`、池状态、两本账、`board.log`、探针连接串与 `probes/**`、`codex-*.txt`、`*.tmp`)加登记簿;`MODEL_OUTPUT`(`evidence` / `review` / `decompose`)不进表。
3. `--prompt-selftest` 扫源码里所有写进 `<data>` 的字面文件名,归不进两表之一就红;并断言没有规则盖住证据路径。looptest ⑭ / reviewtest §2b 改为从真 loop 的 argv 断言新写法。
4. `doctor` ⑤d:让 `verify_lib.py --print-deny-rules` 打出本部署实际会发的规则,拒绝单斜杠与 Write/Glob/Grep 写法;语义仍只能靠真 CLI 量。
5. SECURITY / README 按平台与 CLI 版本限定「实测有效」。

未做、要在远程机上做的:Windows 盘符形的复测(§6 第一张表就是脚本清单)。
