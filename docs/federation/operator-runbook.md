# Windows 共享看板操作手册

本手册汇总当前实现的操作顺序、命令入口和失败时应保留的状态。它不代表 G11 已发布；两台实体机、桌面客户端、真实执行器和持续观察仍按实际回执验收。所有数据库命令使用明确的本机绝对路径，凭据及运行证据放在本机私有目录。不要在两台机器间共享一个可写 SQLite 文件。

## 开始使用

1. 选择已核对的固定源码版本，记录版本、代码/配置摘要、本机 node_id 与 epoch。开发分支前进不自动升级运行节点。准备目录、工具预检和双机身份回执见 [实体试点](windows-pilot.md)；首次初始化、重启和改名后核对所有者不变，见 [身份规则](identity.md)。
2. 为具体项目选择参与节点、单一关系登记节点和权限范围。核对现有 Tailscale Serve 配置及精确关闭命令后，在已批准范围启用独立 peer 端口；不代理操作员页面。逐端点签发绑定节点/epoch/服务地址的凭据，执行 hello、错误凭据和越权项目检查，见 [peer 操作](peers.md) 与 [地址绑定](peer-endpoints.md)。
3. 分别启动本机 UI 与 [节点常驻入口](node-runtime.md)。通信配置使用 scheduler:null 可先完成同步接线；只有任务、角色、隔离能力、来源和预算均核对后，才按 [调度流程](scheduler.md) 开启执行。
4. 按 [桌面上下文](desktop-context.md) 接入本机 MCP 与私有 Markdown。实际客户端查询成功才记作桌面连接通过；预检和导出文件存在均不代替客户端验证。Markdown 是带生成时间的摘要，当前任务裁定仍查询看板。

常驻查询与停止使用同一已核对数据库：

~~~powershell
node cli/node-runtime.mjs status --db <本机DB绝对路径>
node cli/node-runtime.mjs drain --db <本机DB绝对路径> --instance <实例UUID> --version <revision> --request-id <新请求UUID>
node cli/node-runtime.mjs cancel --db <本机DB绝对路径> --instance <实例UUID> --version <最新revision> --request-id <新请求UUID>
~~~

status 只读。drain 停止新派发并等待在途任务；cancel 请求受控停止在途执行。requested 只代表请求已落盘，须继续核对 observed_revision、结束状态和停止证据。不要按 node.exe 名称批量结束进程。

## 一次任务的闭环

1. 本机 MCP 创建或拆分任务，确认所属项目、终端、角色与当前版本。树结构通过登记流程提交；图尚未 ready 时不能放行，见 [拓扑操作](topology.md)。
2. 跨端委派先形成意向，由接收端接受；双方确认关系与合同后，核对当前权限、就绪状态和执行许可，再明确放行，见 [端点合同](bindings.md)。关系登记回执本身不是执行授权。
3. 已领取后隧道断开，保留本机运行与证据；对端显示旧观察或待送达。重连使用原请求 ID/游标续传，不因超时重新建卡或领取同一 run。
4. 输出先作为 [候选交付](results.md) 登记。接收方验证实际产物、源码基线与哈希，执行 [独立验证](verification.md)，再由授权身份进行 [集成](integration.md) 和 [完成确认](completion.md)。模型回复、进程退出码和父任务文字都不直接签收。
5. 取消按 [双端取消](cancellation.md) 和 [停止结算](cancellation-closure.md) 处理。没有停止 ACK 时保持待确认；晚到结果保留审计，不覆盖更新后的裁定。

## 每日巡检与故障处理

先查看 [只读未决清单](inspection.md) 和 [健康哨](health-watch.md)，再按对应记录操作。相同请求重放只应用一次；状态/摘要已变化时重新准备计划，不修改旧回执。

| 场景 | 操作顺序 | 预期与停止条件 |
|---|---|---|
| 同步退避或对端离线 | 查看实例及原投递记录；核对网络、凭据和来源 epoch；恢复后继续原操作 | 旧任务不重派；没有持久确认时仍显示待同步 |
| 身份/权限冲突 | 保存原记录；按 [冲突处理](conflicts.md) 刷新状态并作授权裁定 | 不用旧任务版本或其他节点凭据强行覆盖 |
| 未知执行结果 | 查看 dispatch/journal 和实际停止证据；使用已实现的人工失联结算入口 | 不自动重跑、不返还额度；结果未知与已验收严格分开 |
| 节点异常退出、残留锁 | 先查实例身份、进程和运行记录，再按 [锁恢复](runtime-lock-recovery.md) 准备/提交明确计划 | 只清理匹配原锁；缺少停止证明时保留锁和现场 |
| 节点改名 | 按身份命令改显示名，重新查看 owner 和链接 | node_id、既有任务归属不变；不得复制数据库充当新节点 |
| 撤销节点 | 先停止新派发、核对在途任务，再按 peer 文档撤销该对端当前凭据 | 旧权限请求失败；不删除任务与证据或影响其他 Serve 条目 |

告警解除表示下一次观测未再出现该问题，不表示任务已验收或远端已停止。当前健康哨没有完成全部磁盘、预算与认证有效期监控，实际值守配置与责任人仍待发布验收。

## 备份、升级与恢复

1. 停止新派发，等待或按协议结算在途任务；记录仍未知的项。使用 [一致性备份](backup.md) 生成数据库与证据清单，不直接复制正在写入的单个 SQLite 文件。
2. 按 [0.24 迁移说明](migration-0.24.md) 核对兼容性。停止旧代码写入后升级一台，验证身份、结构与授权投影，再处理另一台；禁止旧程序写入不兼容 schema。
3. 升级失败时保留失败目录与日志。需要回退数据库时使用已验证备份，在新目录隔离恢复，见 [节点恢复](recovery.md)。确认原节点和其他恢复副本不能继续写入后，按明确计划激活新 epoch。
4. 使用 [来源恢复](source-recovery.md) 在对端核对新 epoch、恢复链、快照及缺失结果。未核对的旧记录保留待审，不能用低版本快照覆盖同代次新结果。
5. 原登记节点或成员换代后，先核对所有在途确认。没有活动合同和未知操作的项目可按 [图恢复](graph-recovery.md) 创建后继代次、端点重新登记，最后人工放行。活动合同及结果未知操作的完整恢复协调仍是交付待办，不清空旧表绕过。
6. 保留期和归档只按已冻结且实现的策略执行。产物归档迁移尚未启用，不手工删 chunk/transfer 记录释放容量。没有实际启用的网络入口，不执行关闭命令冒充回滚演练。

## 最终交接

维护者接收固定发布版本、角色/配置摘要、逐节点身份及端点、备份位置与恢复责任、告警接收方、未决事项和关闭命令。真实设备、模型调用、72 小时观察及操作者现场验收必须各有对应证据；当前 pending 回执不得改写成 accepted。阶段合同、权重和口径沿用 [实施计划](../多终端共享看板-实施与验收计划.md)。
