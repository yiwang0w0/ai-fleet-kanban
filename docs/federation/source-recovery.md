# 接收端接纳恢复后的来源

源端按 recovery.md 激活备份后生成新 epoch。新凭据不会自动清空接收端游标。接收端必须先取得带来源身份绑定的恢复标记、生成计划并核对摘要，再本地接纳。普通同步仍拒绝未知 epoch。

## 操作顺序

1. 完成源端恢复流程、核对真实停机证据。为接收节点签发绑定新源端 epoch 的独立凭据。
2. 在接收节点生成计划：

~~~text
node cli/source-recovery.mjs prepare --db <接收端数据库绝对路径> --url <固定来源根地址> --credential-file <新凭据绝对路径> --expected-epoch <接收端所见旧代次> --plan-file <新计划绝对路径>
~~~

3. 核对来源 UUID、旧/新 epoch、地址、凭据版本、影响项目、当前副本数、已有缺失项及反向旧凭据撤销信息。计划不能包含 token 原文。任何副本/游标/登记变化都可能使计划失效，需要重新核对。
4. 使用刚核对的计划摘要：

~~~text
node cli/source-recovery.mjs accept --db <接收端数据库绝对路径> --plan-file <已核对计划绝对路径> --plan-digest <已核对摘要>
~~~

5. 按 sync.md 使用新凭据拉取各授权项目。接纳不会启动同步循环或执行器；已有 watch 会在下一轮使用其配置的凭据文件。旧凭据文件不会被自动覆盖，需要给新 watch 明确指定新文件。
6. 查看副本、待恢复项目和历史：

~~~text
node cli/sync.mjs status --db <接收端数据库绝对路径>
node cli/sync.mjs replicas --db <接收端数据库绝对路径>
node cli/source-recovery.mjs history --db <接收端数据库绝对路径> --origin <来源UUID>
~~~

这些命令只接受显式路径；计划文件独占创建，不能覆盖已有文件。prepare 完成同步 schema 迁移及认证观察，但不改变来源代次或业务任务。accept 在本地事务提交后输出回执；终端输出丢失时应查询 history，不要据输出缺失推测未提交。

## 核对的内容与权限

hello 响应以可选 extensions.source_recovery 返回最小恢复标记：来源 UUID、恢复 ID、旧/备份/新 epoch、激活时间和源端回执摘要。不传源端目录、停机证据引用、完整回执或其他项目计数。该能力名为 source-epoch-recovery-v1；未恢复节点没有该标记。

计划绑定接收数据库真实路径、接收节点身份、固定地址、新凭据路径/key/version、来源标记、当前来源相关状态摘要、影响项目与本地反向凭据。accept 再次认证握手，并在事务内重新核对这些字段。摘要证明核对对象未变，不是身份凭据，也不证明其他机器已停机。

接纳在同一事务内登记旧 epoch 的永久拒绝记录、切换来源认可的 epoch、把已知及新获准项目设为待快照，并清理旧暂存。若本机仍有发给来源旧代次的有效凭据，一并撤销、递增版本并留审计。后来给该旧代次重新 grant 也被拒绝；反向通信需重新签发绑定新代次的凭据。

握手只是当时的认证观察，没有跨节点原子锁。每个后续分页/增量请求仍在来源重验凭据；握手之后被撤销时，接纳记录可以处于 pending，但不能凭它继续访问来源。已合法交付的数据不会因之后撤销而被远端抹除。

## 副本切换和旧结果

每个项目独立恢复。批准后旧副本仍可读，recovery_state=pending_snapshot；accepted_source_epoch 是已认可的新代次，source_epoch 仍是这份可见数据实际所属代次。普通增量不能跳过待恢复快照。

分页先持久暂存，完整验证后才在一个事务内：

- 归档旧副本、游标和快照锚点。
- 安装新代次的投影与游标，并写入已接收事件身份/摘要。
- 为旧备份缺少的可见任务保留 recovery_state=missing_review 的历史副本。
- 把该项目标为 installed，最后清理暂存；事务提交后才发送 ACK。

因此允许新代次来自更旧备份、任务版本降低，但旧结果仍可通过 history 核对；同一代次内仍拒绝回退。task_uid、owner 与项目绑定不可借恢复改变。缺失记录不进入本地任务队列、不触发自动补做，也不能直接计作新的完成结果。

来源以后重新发布同 UID/项目的任务或明确撤回时，该缺失记录标记已解决；历史 JSON 保留。当前提供读取和标记展示，不自动把历史结果写回来源，也不自动合并旧产物。人工核对和来源侧受控补救仍需对应业务流程。

多个项目可以分别完成；凭据只准访问部分项目时，其余项目继续 pending 并保留旧数据。再次恢复会归档上一轮待恢复状态、清理其暂存并绑定新的项目恢复代次；不会删除尚未核对的历史结果。

## 离线期间来源连续恢复

例如接收端停留在 E0，来源先后恢复为 E1、E2。现可使用上述相同 prepare / accept 命令，expected-epoch 仍填接收端当前认可的 E0，凭据必须绑定实际 E2。不得手改游标、来源表或凭据 epoch。

单次恢复仍使用原标记和 v1 计划/回执，不要求新能力。跨过中间代次时，来源需声明 source-epoch-lineage-v1；接收端才会请求 POST /peer/v1/recovery/lineage，正文为 node_id、from_epoch、to_epoch。该入口只读返回请求范围内的链，需当前有效 sync:pull 授权，并在请求体收完后再次核对授权；不会在每次 hello 中广播全部恢复历史。

来源从当前代次沿本机 board_recoveries 的 retired_epoch 逐步回溯，要求每个代次只有一个匹配回执，最多 64 次。返回链只包含原 v1 脱敏标记及链摘要，不暴露备份目录、完整回执、人工证据引用、凭据或项目计数。接收端核对来源 UUID、起终点、相邻代次、唯一恢复 ID、无循环、链摘要，以及末端标记与认证 hello 一致。该记录证明的是认证来源声明的连续历史；摘要不是签名，不证明实体机器已经停机。

跨代计划使用 ai-fleet-source-acceptance-plan/v2，增加 lineage。管理者应核对每一步 retired_epoch → new_epoch、激活时间和回执摘要，再提交准确 plan_digest。accept 会重新握手和读取同一条链，来源历史、凭据或接收状态变化均拒绝旧计划。成功回执为 ai-fleet-source-acceptance/v2，保存完整脱敏 lineage 和 retired_epochs；E0、E1 在同一事务内永久拒绝，反向旧凭据也按原规则撤销。任何中间写入失败整体回滚，不部分退役。

接纳只建立新代次及待快照状态。旧可见结果保留到新快照完整验证后才切换，较旧备份缺少的任务仍进入 missing_review；项目权限、分页、只读副本和不自动补做的边界不变。

若从更旧备份恢复导致中间回执未保留，返回 RECOVERY_LINEAGE_MISSING；超过 64 步返回 RECOVERY_LINEAGE_LIMIT，重复/循环回执或不一致链也拒绝。backup_epoch 恰好等于 E0 不能替代 E0 → E1 的缺失记录。当前不会伪造或自动补入丢失历史，也没有绕过缺链的开关；需先通过独立运维核对恢复历史。来源与接收端都需使用支持新能力/v2 计划的版本。

## 升级与验证

当前同步 schema 为4；跨代恢复本身不增加数据库 schema，使用既有恢复历史及退役记录。旧版迁移与节点身份不变，事务化建立来源代次、恢复历史、缺失记录及任务项目登记。升级前备份并停止旧 peer/sync 进程，旧版不支持新版数据库。保持 Node24。

新版快照为所有实际收到的记录保存 inbox 身份/摘要，防止后续恢复复用已观察事件身份。旧版只留锚点的历史不会凭空补造；既有可用回执继续保留。恢复历史和缺失内容可能含私密正文，只供本地授权运维查询，不自动对等共享。
