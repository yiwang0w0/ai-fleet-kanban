# 来源验收、双端完成与父任务推进（Windows）

本协议接续 [实际文件传输](artifact-transfer.md)、[来源独立检查](verification.md) 和 [来源 Git 合并](integration.md)。来源操作员明确接受已合并的实际产物后，执行端核对原候选及停止证据；双方再向同一个关系登记节点确认同一份完成合同。取得双端完成登记回执，才可各自原子结算任务。工作节点的报告、测试退出零或单方声明不能使来源任务通过。

## 授权与数据合同

新增能力 `delegation-completion-v1`。来源到执行端的凭据需要 `delegation:complete`；两个端点到固定登记节点的凭据需要 `relations:read` 与 `relations:complete`，并保留各自原有授权范围。新 scope 不会自动授予旧凭据。若轮换来源到执行端的凭据，需通过既有 `source_ready` 消息重新确认该凭据版本的绑定；旧授权投票不计入当前双端确认。

本机 `prepare` 是明确的来源操作员验收决定，必须给出完成 UUID、来源任务当前版本、固定合并 UUID 和验收说明。此入口不加入执行身份的 MCP 工具或对端网关。准备时重新读取实际合并引用、产物和独立检查，并在来源写事务中重验任务、权限与实际 Git 引用。人工闸、待决策任务、未完成依赖或本地子任务均阻止接受。

完成合同绑定来源/执行节点及 epoch、关系合同、候选正文摘要、两端任务版本、产物清单、验证和合并回执摘要、来源实际 commit/tree、执行停止范围与操作员说明。合成执行必须显式 `--allow-fixture`；回执保留 `fixture_runs`，不能把这种任务结案当成真实供应商调用或两台实体电脑验收。

## 操作顺序

1. 来源：`node cli/completion.mjs prepare --db <来源DB> --integration <合并UUID> --id <完成UUID> --version <来源任务版本> --note <验收说明> --accepted-rev <治理树验收文件>`。
2. 来源：`send --db … --id … --url <执行节点URL> --credential <完成授权凭据>`。执行端匹配实际候选、任务版本、绑定授权、停止证据和封存范围后持久保存就绪回执。
3. 双方分别：`register --db <各自DB> --id … --mode approve --url <登记节点URL> --credential <登记凭据>`。登记节点在自己的 DB 中串行检查双方当前凭据、同一合同摘要和图版本。它记录不可变完成证据、递增图版本，并从活动图排除该关系；原关系边和全部审批历史保留。
4. 另一方尚未确认时，使用 `register … --mode poll`。网络中断或 ACK 丢失后重试原操作，不生成另一个完成编号。未知请求继续使用原 request_id；只有明确的图版本冲突才允许重新取版本建立下一次请求。
5. 双方分别：`settle --db <各自DB> --id … --accepted-rev <治理树验收文件>`。来源再次核验实际文件与合并引用；任务、正向裁定、绑定结束和结算回执在同一个本地事务内保存。执行端不能用来源回执替换别的候选或新一轮任务。`get --db … --id …` 可读取历史状态。

登记节点就在端点本机时，register 可省略 URL 和凭据，仍通过固定登记身份和成员检查。来源与登记服务共用同一节点的两节点布局已由实际本机 HTTP 测试覆盖，无需第三个节点；这不代替两台实体电脑的验收。完整参数见 `node cli/completion.mjs --help`。CLI 不修改真实 accepted_rev，也不默认选择部署数据库。

## 断线、故障和范围保护

本地意图、就绪回执、登记尝试、登记完成证明与端点结算分别持久化。重复相同请求返回同一历史结果；更换正文或摘要被拒。执行端 ACK 丢失、登记完成 ACK 丢失或数据库重开后均恢复原记录。任务结算失败会一起回滚任务状态、正向裁定、绑定关闭和临时写许可。

提交验收意图会固定当前本地任务子树：不能改写成员、追加子任务或迁移其父子关系，也不能把同一意图改成取消或退回。已发生的来源 Git 更新不因此回滚。合并引用被移动、授权被撤销或停止证据失效时，保留记录并等待明确处理，不覆盖现场、不伪造成功。节点恢复换代保留历史，但旧 epoch 的完成意图不能继续执行。

关系完成只在双方分别使用有效凭据确认后产生。撤销或轮换凭据使该版本未完成的投票失效；单方提供一份声称来自另一方的回执不能替代另一方的真实投票。来源和执行端可在不同时间结算；尚未结算的一端保留本地保护，重连后继续。

## 父任务与存储升级

来源独立检查通过只给该来源任务写入验证结果，不触发原生 `proves_parent` 或 `oneof` 自动结案。父任务保留自己的验收责任；仅在未设人工闸、所有本地子任务完成、已有旧审阅且没有其他委派或拓扑保护时，清除旧审阅标记并重新送审。同组兄弟任务不会因此自动通过。

关系 schema 升为 2，端点绑定 schema 升为 3，新增 completion schema 1。绑定表使用可回滚的加列迁移保留旧状态与内容，完成历史另表保存；逻辑状态为 completed，旧准备/确认记录仍可追溯。部署前须备份并停止旧进程，再一起升级参与端点与关系登记节点。新旧版本不混跑完成协议。

当前实现仍需两台实体机、三种原生执行器、Windows 权限隔离、后台调度、全局 UI 与完整阶段验收。独立 Git 副本和 Windows Job 不提供文件或网络沙箱。本协议测试使用的合成运行不会计入用户授权的三种真实最小任务额度。


## 恢复后的封存来源证据

正常接口继续拒绝旧代次的完成和验证。需要保留证据给恢复流程使用时，可运行 [只读来源复查](completion-evidence.md)：实际核对原验证输入、固定程序、产物和 Git 合并，不重跑模型、不写数据库，也不自动验收。已接受的结果仅作为历史显示；完整完成恢复协调仍须另行完成。

执行端对应的保留任务范围、停止观察、产物及历史结案也可通过 [执行端复查](completion-evidence.md#执行端保留证据) 核对。版本变化会明确列出待协调项，观察结果不放行任务或新签验收。
