# 运行产物的文件传输与内容核验

本功能以 Windows 为唯一目标环境。它补上跨节点交付的实际文件通道：执行端从已经结束的文件会话生成 Git 提交，捕获实际对象与文件字节，接收端持久保存并核对原始批准基线。收到文件和内容核验通过均不代表任务验收通过。

## 使用顺序

1. 执行端完成 workspace-files 运行与 `workspace commit`，按现有 `result prepare` / `result send` 回传候选报告。
2. 来源端使用 `artifact target` 为该候选指定本机仓库映射、精确批准基线，并明确允许读取完整基线。未修改文件也参与完整 Git 树与内容摘要复核，因此普通局部文件读取权限不自动升级为完整基线权限。远端不能提交本机绝对路径，也不能替换已固定的映射。
3. 执行端使用 `artifact prepare` 从候选绑定的实际 run/dispatch 工作区捕获文件包。调用者只能指定候选与传输 ID，不能传入自称已完成的 commit、清单或文件字节。
4. 反向 peer 凭据需明确包含 `peer:handshake`、`delegation:result`、`artifact:write`。执行端使用 `artifact send`，每轮默认最多 64 个分块；返回 `more` 时继续同一命令，`retry_pending` 时等待连接恢复后重试。不会重新调用模型或新建运行。
5. 来源端 `artifact verify` 从本机登记仓库读取真实批准基线，检查收齐的包及完整目录。该步骤在本机独立执行，避免把 Git 全量读取放入 HTTP 请求和数据库写事务。完成后再次 `artifact send` 可把内容核验回执同步回执行端。
6. `artifact get` 显示元数据和当前回执。后续独立测试、源仓 CAS 合并、来源正向验收及父任务推进仍需各自的实现与证据。

运行 `npm run artifact -- --help` 查看精确命令参数。所有命令必须显式指定数据库；不默认连接当前部署。

## 数据与协议

`workspace_artifact_offer` 包含传输 ID、候选 ID/正文摘要、运行产物清单摘要、实际包 SHA-256、总长度与固定分块大小。产物清单绑定 project/repo、节点及恢复代次、task/run/dispatch/agent、原始 commit、交付 commit/tree、完整内容摘要、文件会话摘要与 revision、启动摘要和停止证明；必须与已收到的候选一致。一个候选只有一个不可替换的文件传输。

包 `ai-fleet-git-package/v1` 保存实际原始 Git commit 字节、完整清单，以及每个净写入文件的 base64 字节。删除项不携带伪造内容。单文件最多 8 MiB，净变化最多 256 文件、32 MiB，包最多 48 MiB。分块为 64 KiB；完整基线仍受既有仓库读取器的数量、大小、路径、符号链接/子模块和时间边界约束。

接收端使用本机 SQLite BLOB 保存连续分块。分块长度与 SHA-256 校验后，内容和审计在同一事务写入；完全相同的重复块返回当前进度，不重复保存。同一位置的其他内容、越序分块、清单替换均拒绝。接收端数据库中的连续块数是恢复游标，发送端不会因回执丢失另建传输。传输包与清单合计预留容量最多 256 MiB，旧代次及已完成记录仍计入；容量不足需明确处理保留策略，当前功能不会自行清理历史。

节点接口为 `/peer/v1/artifact/offer|chunk|seal|status`，协商能力为 `artifact-transfer-v1`。每次请求先认证，再限长读取正文，并在写事务内重新验证凭据、项目、节点代次与权限。HTTP 不提供完整基线读取或文件执行接口；仍由既有回环监听器承载，Tailscale HTTPS 入口另行部署。

## 回执与边界

- `receiving`：至少已登记文件传输，可通过已存分块恢复。
- `received`：完整包已持久化，实际总字节与包 SHA-256 匹配；内部 Git/文件内容尚可能不合格。
- `content_verified`：从接收端实际批准基线重建完整交付目录，核对 Git commit/父提交/tree/blob、各文件 SHA-256、原文件摘要、允许的净变化与完整目录摘要。
- `cancel_pending` / `rejected`：停止新文件写入与核验，既有内容保留。旧节点代次、恢复隔离副本、失效凭据也不得继续。

以上状态的 `accepted` 始终为 `false`。核验不修改源仓 HEAD、工作目录或任务状态，不启动测试或供应商。回执不可覆盖；来源核验完成后，其回执仍只是内容证据，不能替代独立审阅。捕获已核验内容时继续检查当前节点、候选和授权，备份恢复后的旧记录仅作为历史保留。

## 验证范围

专项使用真实临时 Git 仓库、SQLite 与本机 HTTP，验证 MCP 文件输出、丢失分块 ACK、收发数据库重开、限定每轮分块数、幂等重放、内容损坏、路径/基线/运行错配、取消及退回、审计写入故障、凭据撤销、容量与备份恢复。另将传输的模块写入独立临时目录执行，确认字节确实可用；这属于隔离测试，不是产品中的独立验证器或实体两机验收。

三种供应商的真实任务额度未在本功能测试中使用。具体已完成结果和源码摘要见配套证据文件；实现仍须经过完整回归与准确提交的 Windows CI。

## 二进制内容的恢复摘要

恢复校验以 BLOB 的实际字节长度和 SHA-256 绑定完整二进制内容，不把每个字节展开成 JavaScript 数字属性；其余 SQLite 标量编码与表/主键顺序保持。原算法在隔离测试中仅 8 MiB BLOB 就耗尽 192 MiB V8 堆，因此本批修正该路径，并增加 48 MiB、有约束内存的完整字节变更检查。

含 BLOB 的旧恢复计划摘要会因此改变，需重新准备并审阅恢复计划；旧摘要不会自动被当作当前数据的许可。修正不会修改已有文件、数据库字节或历史回执。
