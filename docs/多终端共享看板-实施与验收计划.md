## 0. 使用方式与完成定义

这份计划把用户已经确认的目标、建议采用的设计和需要实测的假设分开记录。各阶段依赖前一阶段的验收回执推进，不能用“代码已写完”替代“阶段通过”。

最终交付应满足：用户指定的两台 kanata 实体电脑通过 Tailscale 互联；各终端拥有自己的任务根、本机数据库、MCP 接口、调度器和 agent 身份；全局视图能够显示各终端的任务树、跨端委派、依赖和证据；已领取任务在隧道断开后继续本机执行，重连后补齐结果；重复消息、进程重启和短暂断网不会产生重复任务或重复验收。

V1 的节点数量、时间阈值、预算和保留期均为建议值，在 G00 冻结后成为验收合同。文中的新增模块名、接口名和命令协议是设计建议，不代表仓库已经提供这些功能。

## 3. 目标架构

每个节点包含本地看板、单写者数据库、确定性调度器、MCP 服务、执行器适配层、联邦同步网关和证据存储。全局视图由各节点的权威数据与已同步副本组合；它不必依赖一个集中持有所有任务的数据库。

~~~mermaid

    subgraph NET[Tailscale 私有网络]
        A[终端 A 的联邦网关]
        B[终端 B 的联邦网关]
        C[终端 C 的联邦网关]
        A <--> B
        B <--> C
        C <--> A
    end
    A --> AB[本地看板与数据库 A]
    B --> BB[本地看板与数据库 B]
    C --> CB[本地看板与数据库 C]
    AB --> AM[MCP 接口与本机调度器]
    AM --> R[规划 / 架构 / 实现 / 测试 / 审阅身份]
    R --> E[Claude / Codex / Zcode 适配器]
    AB -.授权状态副本.-> V[可在各终端打开的全局视图]
    BB -.授权状态副本.-> V
    CB -.授权状态副本.-> V
~~~

### 3.1 必须成立的系统约束

1. 所有权与执行权分别记录。owner_node_id 表示谁维护任务状态，executor_node_id 表示本次在哪里执行；V1 委派通常在接收节点新建其拥有的关联任务。
2. 本地 parent_uid 构成树；delegation 与 depends_on 表示跨端关系。跨端委派保留来源关联，不把远端任务的副本混入本地领取队列。
3. 远端不能直接修改别的节点数据库。提交命令后，由权威节点校验权限和 expected_version，再产生事件。
4. 通信允许重试和重复投递；事件应用、委派建卡及验收回执必须幂等。不能承诺任意外部副作用“恰好执行一次”。
5. 调度器以本地事务/锁保证同一任务的同一有效 run 不被重复领取；worker 崩溃后的重跑使用新 run_id，并说明原因。
6. 最终状态由权威节点和授权验收者确认。模型文字、自报 verify_ok 或其他终端缓存中的“完成”不能直接关闭原任务。
7. 隧道失联不触发远端租约回收。只有任务的权威节点监督本机 worker 的心跳、死亡和回收。
8. 全局视图允许暂时滞后，必须显示最后同步时间和来源；不把缓存的在线状态当成实时保证。
9. 每次运行绑定角色章程、权限配置、代码/工作仓版本和预算快照。配置更新不悄悄改变在途任务。
10. agent 的消息、远端证据和文件内容均按任务数据处理，不能借其内容绕过调度、权限或验收规则。

### 3.2 跨端关系为何需要单独登记

如果 A 和 B 各自离线添加“A 等 B”和“B 等 A”，两边的局部检测可能都通过，合并后却成环。因此 D07 建议为每个协作项目指定一个关系登记节点：新增跨端依赖按关系版本串行验证，成功后返回确认回执；未确认的关系不驱动执行。

它可以复用某台现有终端的模块，不要求额外部署一台总控服务器。它离线时，已领取任务继续执行，已确认关系保持有效，新跨端关系进入待确认。V1 不自动切换登记节点；未来若要求该部分高可用，应另做有一致性协议的扩展。

本地任务树仍由各自节点维护。新委派可以先生成意向，只有目标接受、关系登记成功后才放行；失败或超时保持可恢复记录。跨节点存在连接不意味着它们可以直接领取彼此的任务。

## 4. 数据与接口合同草案

### 4.1 最小数据对象

| 对象 | 最少字段 | 约束 |
|---|---|---|
| Node | node_id、node_name、identity_binding、protocol_version、capabilities、key_version | ID 稳定；名称唯一规则在 G00 冻结；改名不改任务归属 |
| Role | role_id、charter_digest、tool_profile、runtime_policy、budget_policy | 角色不绑定单个模型品牌；权限按能力检查 |
| Task | task_uid、本地 id、owner_node_id、root_uid、parent_uid、role_id、state_version、status | task_uid 全局唯一；既有本地数字 ID 保留以兼容旧入口 |
| Run | run_id、task_uid、attempt、executor_node_id、agent_instance_id、policy_digest、state | 重试有新身份；终态与工作进程退出分别核对 |
| Delegation | delegation_id、source_task_uid、target_node_id、target_task_uid、state、idempotency_key | 一个委派键最多生成一个接收任务 |
| Relation | relation_id、graph_id、graph_epoch、graph_version、from_uid、to_uid、type | 新跨端关系需登记确认；拒绝循环和过期版本 |
| Event | event_id、origin_node_id、origin_epoch、seq、aggregate_uid、aggregate_version、payload_digest、schema_version | 顺序使用序号与版本，时间戳只供显示；同 ID 不同内容必须隔离并告警 |
| Outbox/Inbox | event_id、peer_id、durable_state、ack_cursor、retry_at | 状态变更与 outbox 同事务；远端落盘后才确认 |
| Artifact | artifact_id、task_uid、run_id、repo_id、commit_sha、sha256、size、relative_path | 内容地址与哈希可验证；禁止信任远端传来的绝对路径 |
| Verification | receipt_id、task_uid、run_id、artifact_digest、verifier_id、policy_version、result | 验证者受信；回执绑定当前交付，旧回执不适用于新版本 |
| GateReceipt | gate_id、plan_version、code_sha、evidence_digest、decision、reviewer、time | 未填写不能视为通过；关键节点另含操作者决策 |

origin_epoch 用于区分节点正常运行、备份恢复及重新登记。恢复后必须协调新 epoch、游标和快照，不能把已用过的事件 ID/序号换内容重发。

### 4.2 状态分别管理

| 状态域 | 建议表达 | 不可混淆的情况 |
|---|---|---|
| 现有任务状态 | 沿用 not_started / in_progress / waiting / done | “终端离线”不新增为任务失败状态 |
| 任务执行 run | queued / running / succeeded / failed / uncertain / cancelled | 进程退出成功不直接等于任务验收通过 |
| 节点连接 | online / suspect / offline / revoked | 缓存中最后在线不代表现在可访问 |
| 同步 | pending / sending / acknowledged / quarantined | 本机完成、待同步可以同时成立 |
| 委派 | proposed / pending / accepted / rejected / result_ready / settled / cancel_pending / cancelled | 取消未被接收方确认时不能显示已取消 |
| 计划阶段 | planned / ready / in_progress / verifying / accepted / blocked | 这是规划清单状态，不直接扩展现有任务四状态 |

### 4.3 接口边界

建议的本机 MCP 工具包括：list_nodes、list_roles、create_task、split_task、request_assignment、delegate_task、get_task、report_result、request_cancel、get_evidence、get_sync_status。具体名称在 S02/S04 冻结。

这些工具通过服务端身份与作用域验证执行。worker 只能操作自己的有效 run；协调身份只能在已授权项目和终端中提交分派；reviewer 的回执权限与操作者最终裁定分开。agent 不直接获得远端操作员令牌、任意命令执行入口或全局凭据。

peer API 单独承担节点握手、能力交换、事件批次、游标确认、委派请求/回应、关系登记、证据清单和文件传输。连接鉴权、协议版本、数据大小、授权项目与消息幂等均在网关校验。

Tailscale 提供私有连通和访问控制；应用仍需实现任务级授权。Serve 可代理本地服务，Grants 可描述允许的连接和应用能力。[Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve)、[Tailscale Grants](https://tailscale.com/docs/features/access-control/grants)。这些文档支持网络层选择，不构成本计划分布式一致性的证明。

## 10. 建议质量指标与测量条件

| 指标 | V1 建议验收值 | 测量口径与限制 |
|---|---|---|
| 权限越界 | 必选负向场景 0 次成功越权 | 覆盖 peer、worker、reviewer、UI、artifact 各入口 |
| 任务/证据丢失 | 必选场景中 0 件已确认数据丢失 | “已确认”指应用持久提交与接收确认，不涵盖未落盘断电数据 |
| 重复逻辑建卡/验收 | 重放测试中 0 次 | 不等价于任意外部 API 副作用恰好一次 |
| 在线状态传播 | p95 ≤ 5 秒 | 3 节点、RTT ≤ 100 ms、可用带宽 ≥ 10 Mbps、单事件 ≤ 16 KiB；直连/中继分别记录 |
| 重连补齐 | 1000 事件且总量 ≤ 16 MiB 时 ≤ 60 秒 | 不计大文件传输；从隧道实际可用开始到接收确认 |
| 离线运行 | 必测 30 分钟；扩展演练 24 小时 | 允许处理已领取任务；模型网络可用性另记；不测试不存在的完全离线云模型能力 |
| 任务数据规模 | 3 节点合计 10000 卡、100000 事件 | 固定中等配置试验机；测试查询分页、搜索、同步积压及磁盘增长 |
| 全局列表查询 | p95 ≤ 1 秒 | 每页 100 条；不把网络加载和模型调用计入数据库查询 |
| 暂停新分派 | 本机 ≤ 5 秒生效 | 远端必须等命令送达；断线时不能承诺即时停止 |
| 子进程停止 | 本机收到取消后 ≤ 30 秒或报告不可终止 | 按运行时能力与平台实测；超时需升级处理，不能虚报已停 |
| 真实模型覆盖 | 每类至少 1 个可复现任务，加跨端审阅 1 次 | 用量、失败、结果正确性分别记录；这不是模型优劣统计实验 |
| 观察窗口 | 连续 72 小时 | 包含离线与重启；无 S0/S1，新问题重置受影响验收窗口 |
| 备份恢复 | RPO ≤ 24 小时，RTO ≤ 60 分钟 | 初始建议；覆盖权威节点完全损坏后的恢复，不能宣称零丢失灾备 |

硬件、网络或业务要求不同，G00 可调整这些数值并记录原因。指标调整后保留旧结果，不用新阈值改写历史测试结论。

## 11. 故障、回退与运行边界

### 11.1 故障处置规则

| 故障 | 当下行为 | 恢复与验收要求 |
|---|---|---|
| Tailscale 中断 | 继续已领取本地任务；进度、结果进入持久 outbox | 恢复后交换游标，补发并去重；不重新领取同一 run |
| 模型服务不可用 | 保存已有产物，记录等待/失败原因，按预算有限重试 | 恢复后由本机权威状态决定继续或新 run；不无限调用 |
| 本机 worker 崩溃 | 本机监督器核实退出并记录 uncertain/failed | 不确定是否产生外部副作用时升级裁定；幂等任务才能按策略自动重试 |
| 节点失联 | 对外显示未知/离线，不夺取其任务所有权 | 联系原节点或走灾难恢复；不能只等超时就认为原任务停止 |
| 图登记节点失联 | 已确认关系继续生效，新跨端边等待 | 恢复原节点；V1 不自动选新主；有状态转移须单独验收 |
| 事件冲突/损坏 | 隔离冲突批次，保持最后可信版本 | 核对原始事件与权威快照，禁止按最后时间戳盲目覆盖 |
| 磁盘满 | 拒绝不能持久保存的写入并告警 | 不提前 ACK；释放空间后重试，保全未确认数据 |
| 取消结果晚到 | 保留结果和原 run 信息，标记已过期或待裁定 | 不覆盖取消/新 run；由任务所有者按当前状态决定接纳 |
| 凭据撤销 | 已联网节点按策略拒绝新操作和重鉴权连接 | 离线节点无法即时收到撤销；重连后先验证身份再接收新命令 |
| 原节点与恢复副本同时出现 | 拒绝重复身份并暂停新增远端写入 | 人工隔离旧节点、核对 epoch/运行记录，确认唯一写者后放行 |

### 11.2 回退顺序

1. 在受影响节点停止新任务领取和新跨端放行，保留已领取任务的可见状态。
2. 按冻结策略等待在途任务结束或发出取消；取消未确认的任务保持待处理。
3. 记录 outbox/inbox 游标、run 状态、代码与配置摘要，制作一致性备份。
4. 若 schema 兼容，回退代码并校验；若不兼容，使用已演练的备份恢复，不把旧程序直接连到新 schema。
5. 恢复副本先保持与 peers 隔离，核对身份、epoch、凭据和未确认运行。
6. 只读连通验证后恢复事件同步，确认没有重复执行，再逐节点恢复领取。

本计划 V1 不包含失联节点自动夺权、跨节点共享一个可写 SQLite 文件、任意外部系统的恰好一次副作用、自动公网发布或自动部署生产业务系统。需要这些能力时另建范围与验收阶段。

## 12. 缺陷等级与停止条件

| 等级 | 判定例子 | 门禁规则 |
|---|---|---|
| S0 | 凭据泄露、未授权执行、任务/证据不可恢复丢失 | 立即停止相关入口和新分派，保全证据并回退；不得发布 |
| S1 | 重复执行/验收、错误所有权、依赖死锁、断线无法恢复、预算失控 | 阻止进入下一阶段，修复后重测受影响链路 |
| S2 | 有明确替代路径的性能不达标、可恢复的局部显示/操作问题 | 必须记录影响；需 OP 接受的例外包含责任、到期日和替代控制 |
| S3 | 不影响正确性的文案、轻微样式问题 | 可列入后续任务，但不伪报已修复 |

“测试没跑”“设备不可用”“权限语义未知”属于未验证或阻塞，不是低等级缺陷。必选证据缺失即不能通过对应门禁。
